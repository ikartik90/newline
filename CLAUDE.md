# Newline

A local-first rich text note editor. Electron (electron-vite) with a React 19 renderer styled in Tailwind v4, SQLite (better-sqlite3) as the on-device store, and one Cloudflare Worker (`worker/`, D1 + R2) as the whole backend: sign-in sessions, notes sync and media. Google is the identity provider; there is no Firebase. A note is kept as MDX text, a closed dialect that is a syntax and never code, and nothing else: main and the Worker hold a note's body as text and never as a tree.

The editor is a port of the article editor in the sibling repo `../kartik.to`. That repo is a READ-ONLY reference: never edit, build in, or run mutating commands there. Its `DESIGN.md` is stale; token values come from its `panda.config.ts`.

## Commands

- Dev: `npm run dev`
- Build: `npm run build` (then `build:mac` / `build:win` for installers)
- Test: `npm test` (vitest, three projects: `renderer` in jsdom, `shared` and `main` in node); `npm run test:watch`
- Typecheck: `npm run typecheck`
- Look at the editor in a plain browser (no sign-in, no Electron): `npm run dev`, then open http://localhost:5173/harness.html — a dev-only page (`src/renderer/harness.html`) that mounts the editor with a sample note; it is not part of the build. http://localhost:5173/shell-harness.html (`src/renderer/shell-harness.html`) is the same for the whole shell — sidebar, command menu, dialogs — on an in-memory stand-in for the Electron bridge; one of its notes, Written in MDX, holds more than paragraphs (a colour, a mark, a list under an item, a size).
- Look at a note beside its MDX: http://localhost:5173/prose-harness.html (`src/renderer/prose-harness.html`), the editor's body on the left and the MDX it writes on the right, live. Dev-only too.
- Lint / format: `npm run lint`, `npm run format` (prettier: no semicolons, single quotes, width 100)
- Worker: `worker/` is its own npm package with its own `node_modules`; run its scripts from inside it (`npm test` there runs vitest inside workerd against real D1 and R2 emulations; `npm run dev` serves it on port 8787; `npm run deploy` needs a wrangler login).

## Continuous integration

`.github/workflows/ci.yml` gates every pull request into `main` with four jobs, named as the checks a branch ruleset requires: **Lint & types** (`npm run lint`, `npm run typecheck`), **Unit tests** (`npm test`), **Worker tests** (`worker/`'s own `npm ci`, typecheck and workerd suite) and **Build** (`npm run build`, gated on the first two). A failing run posts one comment on the pull request and edits that same comment on every later failure. `auto-merge.yml` arms GitHub's native auto-merge so a green pull request merges itself; it refuses to arm when the base branch requires no status checks, because auto-merge with nothing to wait on merges immediately. It arms `--merge` rather than `--squash`, because a branch here carries several self-contained commits. Head branches are not deleted automatically — the merge is recorded as `app/github-actions`, which the repository's deletion setting ignores. `release.yml` is separate and runs on a `v*` tag, not on pull requests.

## Conventions

- **Test-first.** Write the failing test, watch it fail, make it pass, refactor. Every directory with logic has a co-located `__tests__/` folder. Presentational-only work is verified in the running app instead.
- **Zod domain entities** in `src/shared/domain/`; derive types with `z.infer`. What crosses the wire is parsed by its schema first (`NotePushSchema`, `NotesPageSchema`).
- **kebab-case file names** for everything new (matches kartik.to and eases cross-referencing). Components export named functions.
- **Native primitives.** Popover, Tooltip, Dialog, Menu, Select/Combobox, Slider, Checkbox and Toggle are the web platform's own, wrapped once in `components/ui/` and styled with Tailwind; there is no component library, and none is to be added. A floating surface is a `popover="manual"` in the top layer, shown with its anchor as the `source` so CSS anchor positioning places it (`useTopLayerPopover`, `[data-popover]` in `main.css`) on the side and end `useAnchoredPlacement` finds room for, chosen again as it scrolls (the browser's own `position-try-fallbacks` are tried only as a popover shows, then kept); a tooltip a `popover="hint"` named by its trigger's `interestfor`; a dialog a `<dialog>` opened with `showModal()`; a menu a `role="menu"` popover (`ui/menu.tsx`); the Select an `OptionList` in a popover (`input/combobox.tsx`); a slider an `<input type="range">`, a checkbox an `<input type="checkbox">`, and a toggle a `<button aria-pressed>`. The platform gives the layer and the placement; the roles, aria, keyboard model and focus return are ours, written and tested in the wrapper (roving focus, arrows, Home/End, type-ahead, Escape through `useDismiss` one layer at a time). A listener on the document whose handler is new at every render keeps the latest in a ref and is put on once: one taken off and put back while a press is being dispatched (the first key after the mouse renders the page again) is never asked about that press (`useDismiss`, the option list's `externalKeys`). A toolbar floating in a popover (`POPOVER_TOOLBAR`: the selection toolbar's rows, a list number's options) stands 2px clear of its options all round, which are 1px apart, so it is `--size-toolbar` tall, a button and those 4px, as the link editor's row is, and the shell is cornered concentric with them (`rounded-toolbar`: a button's corner as it is drawn, 14px of the 16px asked on a 28px button, and the 2px); the slash menu's column (the option list's `menu` tone) is inset and spaced the same, and the Theme icons in Settings, which have no shell round them, keep the 1px between them and no inset. Use the wrappers; do not hand-roll another. jsdom has no popover or dialog methods: `src/renderer/src/test-setup.ts` stands them in, a shown popover carrying `data-test-popover-open`.
- **Icons come from Crest, at https://kartik.to/playground/icons.** Use one already in `src/renderer/src/assets/icons/` only if it is the icon asked for; otherwise take it from the live page (each tile is `data-icon-tile="icons/<uuid>-<name>.svg"` holding its `<svg>`; the `../kartik.to` checkout may lag it), saved under its Crest name with its stroke in `white`, as the others are. If the page has none either, say so; never draw one, take one from another set, or stand in a loosely related icon (a return arrow for an up arrow).
- **Local-first.** The renderer never blocks on the network and never talks to the Worker itself. Writes go to SQLite through `window.api`; main syncs.
- **Frosted shell.** On macOS 27 and later AppKit draws the sidebar itself: a small Node-API add-on of ours (`src/main/native/sidebar-glass.mm`, built into `out/native/` by `scripts/build-native.mjs` from `predev` and `build`) lays an `NSSplitViewController`'s sidebar item, the one Finder's sidebar is, at the bottom of the window, and `src/main/sidebar-glass.ts` keeps it as wide as the page's sidebar (the renderer reports the width, `window.api.window.setSidebarWidth`). The same split view's inspector item, the trailing pane AppKit glazes alike, lies under the Gemma rail while it is open, as wide as the rail (`useRailGlass`, `window.api.window.setRailWidth`): the rail is pinned beside the note as the sidebar is, so where the window is frosted it paints nothing but its sheet fading in under the conversation (clear at its top, solid `bg-bg-sheet` three quarters down, to the rail's foot; it covers the rail's lower 60% at least, climbs with the conversation past that, and covers the whole rail once the conversation fills it; `railFadeHeight`), and the top bar's Gemma toggle takes its level on the glass while it is open. The page is clear over it (`html[data-frosted]`, set by `index.html` before the first paint from `window.api.frosted`, which main hands the window: `isFrostedWindow`); older macOS gets the `sidebar` vibrancy over the whole window instead, and Windows 11 from 22H2 the `acrylic` background material, the OS's own blur either way. Never fake the window's glass with CSS blurs, tints or masks: the sidebar paints nothing, beside the note pane's solid `bg-bg-canvas` (surface 0). Where the command menu cannot be the glass palette (no AppKit glass), it stays in the page as a `material="frosted"` dialog, the `frosted-sheet` utility: the sheet at 72% over a 24px backdrop blur of the page, solid where `backdrop-filter` is unknown, over the page dimmed by 15% black, as the window is under the glass palette (`palette:visible`), and cornered as it is (`rounded-3xl`). Either way the palette stands centred at its full height, 424px, its top kept as the list filters, and never nearer than 24px to the window's sides, 24px under the top bar or 40px above the bottom; past that its list scrolls under the field (`paletteBounds`, the dialog's `palette` placement). As a dialog does, it stays open while another window or app has the keys (the panel doesn't hide on deactivate) and follows the window as it is resized (`palette:fit`); while it shows, the window under it hands the keys back to it. A press on the dim only closes it: the dim outlasts the palette to the end of the press, so the click lands on nothing under it. Where AppKit has the glass, the command menu is the glass palette, a clear, shadowless window of its own (`src/main/command-palette.ts`, its page `command-palette.html`) over the note window, which turns all to glass under it: the sidebar's own glass laid past the window on every side (`windowGlass` in the add-on), while the page fades all it holds in 150ms, so the menu stands straight on the glass, stepping on it as the sidebar's rows do. Settings, the confirm dialog and image insert stand on the same glass, in the page: `material="glass"` holds it while the dialog is open (`hooks/use-window-glass.ts`, `window.api.window.setGlass`, present only where there is such glass) and draws no sheet, rim or dim, and where there is no AppKit glass it is the solid sheet. Main keeps one glass a window, held by the palette and by the page (`src/main/window-glass.ts`): laid at once, lifted only once the last has gone and the page has faded its note back in, so the palette's Delete hands the glass to the confirm without a flicker. Popovers, menus and toolbars stay off it: they point at the note the glass would fade. `bg-bg-sheet` (surface 1) is the solid stand-in for that glass: the sidebar's fill on other platforms, and the fill under every dialog, popover and toolbar. The sidebar is headed by New note and Search and footed by the account menu, the sync status and the app-settings gear (the gear is the app's settings; a note's own are its properties rail, reached from the command menu). One 48px top bar is fixed across the window and holds the sidebar toggle, beside the native traffic lights (`trafficLightPosition` centres them in that bar), and the Gemma rail's toggle at the right edge, 9px in as the sidebar toggle sits in full screen; both stay put as the rails open and close. The sidebar collapses and opens in 150ms, its contents sliding 8px and fading as the note pane's edge glides, floating over the pane as a peeked sheet does so the moving edge never cuts them off, and painting the canvas while it floats so the pane's gliding edge never shows behind the fade (a toggle never slides the sidebar its whole width); collapsed, resting the pointer on the toggle peeks it up over the note pane as a solid `bg-bg-sheet` (`hooks/use-sidebar-peek.ts`), edged by its own 1px divider and kept while the pointer is over it; a click pins it where it stands while only the pane reflows, then its fill fades into the glass, which is laid at the full width at once (`useSidebarGlass`'s minimum) so it never wipes in. The note pane runs flush to the window's edges with its spacing inside it, as the sidebar's is — neither keeps a margin. Never paint the app root. The renderer relays the theme choice to `nativeTheme` (`window.api.theme.setSource`) so the glass follows the app's theme, not the OS's. Other platforms (Linux, Windows before 11 22H2) get a solid `bg-bg-sheet` shell.
- **Security.** The app holds no Cloudflare credentials. Main keeps the Worker session token in `app_meta`, encrypted with `safeStorage`, and is the only process that calls the Worker; the renderer asks main over IPC.
- **Comments are concise and purposeful.** A line or two, saying why — never narrating a change or the bug behind it. If the code already says it, leave it out.
- **Free plan.** The Cloudflare account is on the free tier and must stay unbillable: the backend is one plain Worker with a D1 binding and an R2 binding, and the Worker's `MEDIA_QUOTA_BYTES` keeps stored media under R2's free allowance. Anything paid (placement, CPU limits, observability, queues, durable objects, custom domains) is out.

Data attributes drive state styling exactly as in kartik.to (`data-active`, `data-indented`, `data-align`, `data-slash-anchor`, `data-sidenote-rail`, `data-media-pending`, `data-keyboard-focus`, `data-control-dragging`).

**A note's own sizes.** `text-style-heading-1` to `text-style-heading-4` are the headings, a note's and the app's own: a note's title and the sign-in screen's wear the first, and a heading in a note the one of its level. `text-style-paragraph-md` is the paragraph, and a style can ask another size of it, named as a shirt's is: `text-style-paragraph-lg` a size up and `text-style-paragraph-sm` a size down, worn by a block whose `<BlockStyle size>` asks for it. A quote in a note is set as its paragraphs are. Every line height in `main.css` is a length in rem, never a factor of the size (`src/renderer/src/__tests__/fonts.test.ts` refuses one), and the list markers' box is as tall as the paragraph's line (`--size-list-marker-line`), a list's number set on that same line. There is no title, subheading, prose, quote or fineprint style: the smallest text is `text-style-sidenote`.

**Every divider is 1px.** kartik.to draws its dividers at 0.5px; here a line in the divider token is `border`, `border-t` and the like (or `h-px` / `inset_0_-1px_0`), and the token itself is solid, a shade past its ground (divider 0, 1 and 2 on the canvas, a sheet and a shell), and on the glass divider 3 at 15%, a test keeping it apart from the canvas and the sidebar. Where two lines meet one stops a pixel short (`right-px`, `after:left-px`). `src/renderer/src/__tests__/token-usage.test.ts` refuses a half-pixel divider.

**The lines on a note's words stand at two heights.** A strike goes through the middle of the x-height: `line-through` stands a third of the ascent over the baseline, near the top of a serif's x, and nothing moves it, so `article-strikethrough` is an underline raised half an ex, less half its own thickness, crossing the ink an underline would step round (an underline under struck words crosses it too, `text-decoration-skip-ink` being the words' own). An underlined word's line, a link's and a sidenote's dotted one share one offset, `0.15em` (`article-underline`, `article-link`, `article-sidenote-text`); a link's is a text decoration, 1px and muted, the highlight under the pointer, never a bar in the background, which sits wherever the font's descent ends. `src/renderer/src/__tests__/text-lines.test.ts` holds them.

**A named spacing step shadows a container width.** Tailwind reads `--spacing-*` before `--container-*` for `w-`, `min-w-` and `max-w-`, so `max-w-sm` is 4px, not 24rem; name a container width as `max-w-(--container-sm)`. `src/renderer/src/__tests__/token-usage.test.ts` guards `min-w-` and `max-w-`.

**Every colour is named for its role, as Spotwork's are: `bg-*`, `ink-*`, `border-*`, `outline-*`, then the component, variant and state, `default` written out (`bg-field-default`, `ink-field-muted`, `border-field-focus`). A state is Spotwork's: `default`, `hover`, `pressed`, `selected` (a picked option, a pressed toggle, a checked box), `focus` (a field the keys are in) or `disabled`; only a link is ever `active`.** The CSS variable is the token's name (`--bg-canvas`), `@theme inline` names it `--color-<token>`, and a class is its utility and the whole name: `bg-bg-canvas`, `text-ink-title`, `border-border-divider`, `ring-outline-focus`. A line drawn as a fill (`h-px`) is `bg-border-divider`, a status dot `bg-ink-danger`. A floating sheet's shadow is drawn in `--shadow-sheet`, the colour of the canvas it floats over (surface 0), as `shadow-[0_4px_16px_var(--shadow-sheet)]`; a scrollbar's thumb is `--bg-scrollbar-thumb-default`, surface 1, 2px wide with square ends, and under the pointer `--bg-scrollbar-thumb-hover`, surface 2, and pressed `--bg-scrollbar-thumb-pressed`, surface 3, both 6px wide, in an 8px track that leaves a pixel either side of it at its widest. There is no neutral palette: every grey is base. A border never draws in a bg or ink colour: it compiles, and a field's frame drawn in its fill loses its edge. **Surfaces stand on a scale of primitives, `--bg-0` to `--bg-4`** (base 50 to 400 in light, mirrored as 900 to 500 in dark), declared in `:root` and `.dark` blocks of their own above the system tokens. **Inks stand on `--ink-0` to `--ink-4`**, the surface scale with its themes swapped (base 900 to 500 in light, 50 to 400 in dark), 0 the strongest: `--ink-title` is ink 0, `--ink-body` ink 1, `--ink-list-marker` (a list's numbers and bullets, on no chip) ink 2 `--ink-sidebar` ink 3. A component has an ink of its own, named as its fills are and taken by its icons as by its text: `--ink-button-primary-default` inverse ink 1, `--ink-button-secondary-default` and `--ink-button-tertiary-default` ink 2 (a tertiary icon button's glyph too, and the chip on a picture, which is a secondary button), `--ink-segment-default` (a segment not picked, in a segmented control or a toggle bar) ink 2 and `--ink-tooltip-default` ink 2. There is no shared control or icon ink; `token-usage.test.ts` refuses one. Text inks are named for their role, as surfaces are (`canvas`, `sheet`), never a bare `default`: `--ink-body` is every text that is not a title, kartik.to's `text.default` and `text.body` both, softened with an alpha where it should sit back (`text-ink-body/50`). **The statuses stand on no scale: each is a primitive of its own on a palette step**, declared after its role's scale: `--bg-highlight`, `--bg-danger`, `--bg-warning` and `--bg-success` (the palettes' 100 light, 800 dark), `--ink-highlight`, `--ink-danger`, `--ink-warning`, `--ink-success` and `--divider-highlight` (the palettes' 500 light, 400 dark). Wherever one is drawn it is a system token on it, named for what it is (`--bg-field-selected` and `--bg-mark-default` on `--bg-highlight`, `--outline-focus` and `--border-quote` on `--divider-highlight`, `--ink-error` on `--ink-danger`, `--bg-row-delete` and `--ink-row-delete` on danger's fill and ink); a fill in a status is on the status's bg primitive, never its ink, but a sync dot is the sync status's ink (`bg-ink-sync-synced`), as its words are. No utility writes a primitive: components write the system tokens built on them, and `token-usage.test.ts` refuses a `bg-bg-2`, a `text-ink-2`, a `text-ink-inverse-1`, a `border-divider-1`, a `text-ink-highlight` or a `var(--bg-danger)`. the canvas is surface 0, every sheet — sidebar, dialog, popover, toolbar — surface 1, and what stands on a surface takes the next step up. A secondary button, field or hovered item (`bg-bg-field-hover`) on the canvas is surface 1, and a secondary button's hover or a press (`bg-bg-field-pressed`) the step above it, surface 2; a sheet carries `bg-level-1`, which stands its buttons, fields and hovers on surface 2 and the buttons' hovers and presses on surface 3 (a shell on a sheet, surface 2, carries `bg-level-2`). **The surfaces stack: canvas, a sheet on it, a shell on that.** A shell steps a level above its ground, as a field does, its fill and hover one step up and selected two: surface 1, 1 and 2 on the canvas (`:root`), 2, 2 and 3 on a sheet (`bg-level-1`); a shell never stands on a shell, so `bg-level-2` sets none, and no surface stands on itself. A primary button is the secondary flipped: it takes the same steps on `--bg-inverse-1` to `4`, each step in the other theme's shade (base 800 to 500 in light, 100 to 400 in dark; `--bg-inverse-0`, base 900 in light and 50 in dark, is the canvas flipped; `--bg-inverse-5` to `7`, base 400 to 200 in light and 500 to 700 in dark, are for the glass alone), inked in the secondary's ink flipped, inverse ink 1 (`text-ink-button-primary-default`). The inks have an inverse too, `--ink-inverse-0` to `4`, each ink step in the other theme's shade (base 50 to 400 in light, 900 to 500 in dark), for ink on the inverse. **Lines stand on `--divider-0` to `--divider-5`**, solid, each a shade past the surface step of its number (base 100 to 600 in light, mirrored as 800 to 300 in dark): `--border-divider` steps a level as a fill does, divider 0 on the canvas, 1 on a sheet (`bg-level-1`) and 2 on a shell (`bg-level-2`), and on the glass divider 3 at 15%; `--border-field-default` is divider 2, each declared once on `:root`. On macOS the sidebar's ground is AppKit's glass, not surface 1, so what stands on it — the top bar's toggle too, while the sidebar is open — steps on the glass instead (`html[data-frosted] [data-on-glass].bg-level-1` in `main.css`). A shell there hovers in inverse 5 at 15% and stands selected on inverse 3 at 15%; nothing on the glass rests in a shell's fill, so the glass sets none. No field stands on the glass either, so it sets no field fill: what borrows a field's hover and press — a row, an icon button, a press — hovers as a shell does and presses as a selected shell, and a picked option (`bg-field-selected`) is a selected shell too, inked in ink 2 (`--ink-field-selected`), as a button is. **Nothing on the glass is in the highlight**, unless asked for case by case: there a fill on it (a focused field, a text selection) is a selected shell, an ink on it (a link, the syncing status, a selection's text) ink 2, a focused field's own text keeps its resting ink, a faint selected or focus edge is divider 5 at 25%, and the focus ring and a progress bar are divider 5. The sidebar's resize line, on the sidebar's edge with the note, keeps the highlight under the pointer. A secondary button rests in inverse 7 at 15%, hovers in inverse 5 at 15% and presses in inverse 3 at 15% (`bg-button-secondary-pressed`, set on the glass alone: elsewhere a press keeps the hover); a primary keeps its solid fill. The account avatar's disc (`bg-avatar-default`) is filled on the glass alone, as the secondary's rest. A divider there is divider 3 at 15%. A tertiary button rests on nothing and has tokens of its own, `bg-button-tertiary-hover` and `-pressed`, stepping as a field's hover and press do (surface 1 and 2 on the canvas, a step up on each level) and as the secondary's hover and press on the glass. The chip floating on a picture (`emphasis="glass"`) is a secondary button at 60%, frosted. The utility reassigns **`--bg-field-default`**, `--bg-field-hover`, `--bg-field-pressed`, the primary and secondary buttons' default and hover, the tertiary's hover and press and `--border-divider`, not their `--color-*` aliases: `inline` substitutes the value, so no utility ever reads the alias; never reassign them by hand. `src/renderer/src/__tests__/token-usage.test.ts` guards both.

Write every Tailwind class out whole. Tailwind's scanner reads class names from the source text, so a name assembled at runtime (`` `data-[active]:${tint}` ``) reaches the DOM with no rule behind it and styles nothing; branch between two complete strings instead. Two utilities for the same property in one class list resolve by stylesheet order, not list order — `.flex` is emitted after `.contents`, so an appended `contents` never collapsed a `flex` root. Write the cases as alternatives, never a base plus an override. `components/ui/input/__tests__/option-list-classes.test.tsx` guards both.

## A note's body

A note's body is MDX text, in SQLite `notes.body`, in D1 and on the wire, and nothing else: there is no document tree, no JSON and no `format`. `notes.plain_text` holds its words for FTS search, read from the MDX by `mdxPlainText` (`@shared/mdx/plain-text`): a block to a line, each block's sidenotes after it, a picture its caption.

**MDX, the format notes are kept in.** `src/shared/mdx/` is the dialect: its parser (`dialect.ts`), the readers and writers of a line's runs and marks the editor works through (`reading.ts`, `writing.ts`, `inline.ts`) and `plain-text.ts`. MDX here is a syntax and never code: micromark's JSX extension parses the tags, with no `import` and no `{expression}`, and a tag is read from a closed list. The dialect is CommonMark with strikethrough and tasks (`- [ ]`, `- [x]`), plus `<u>`, `<mark>`, `<Sidenote note="…">` around its run, `<TextStyle color>` around a run and `<BlockStyle size color align indent>` around a block, a colour always a role's name (`highlight`, `muted`, `danger`, `warning`, `success`), a size `sm` or `lg` and an alignment `center` or `right`, left being written as nothing. A task's box opens its line, so a task whose own line is styled is written with the style inside the line (`- [x] <BlockStyle size="lg">Big</BlockStyle>`), an empty task as `- [ ] &#x20;`, and words that only look like a box keep their bracket escaped. Headings map straight (`#` to `####` are Heading 1 to 4), a picture or a clip is `![alt](src "caption")` with no layout, a block indented under a list item is that item's child, and an empty paragraph is a line holding `&nbsp;`. Two things are read and never written: a footnote (`word[^1]` and its `[^1]: …`) is a sidenote on the word its marker follows, two on one word one sidenote, and a footnote no marker points at keeps its words as a paragraph; an address written bare (`https://…`, `www.…`) is a link to itself.

**The editor is ProseMirror, working on MDX.** `src/renderer/src/prose/` holds it and the app mounts its `MdxNoteEditor`; there is no other editor. Its schema (`schema.ts`) is the dialect one to one: paragraph, heading (four levels), blockquote holding blocks, bullet and ordered lists of items that nest, code block, rule, media, and the marks; a block's `<BlockStyle>` is the block's own attributes (`size`, `color`, `align`, `indent`), a list item's `checked` says whether it is a task and whether it is done (`null`, `false`, `true`), and there is no eyebrow, metric or caption. `mdxToProse` and `proseToMdx` read and write the MDX through the same shared readers and writers the document converter uses (`@shared/mdx/reading`, `writing`), and a test holds every note of the shared corpus (`@shared/mdx/__tests__/support/corpus.ts`) to come back from ProseMirror as the text it went in as. `plugins.ts` is what typing does (markdown's signs start their blocks; the keys mark, break, list and undo; an address typed bare is linked at the space or Enter after it, `links.ts`, a `www.` one to `https://`) and `prose-editor.tsx` the React mount, which opens on MDX and hands MDX back on every change. It draws with the components the editor before it had, rather than new ones: `list-markers.ts` draws a list's markers in the `list-marker` utilities (each item's label a decoration, drawn by the item's node view, never part of the text), `slash.ts` answers a slash with `SlashMenu`, a heading offered at each of its four levels and found by `h1` to `h4` too, a Task list found by `todo` too, and the kind the caret is already in left out; a list kind picked on a list item changes that item where it stands, never indenting it (`list-kind.ts`), `selection.ts` drives `SelectionToolbar`, which stands over the first line of the selected words, keeps its place as they are marked and follows them when the note is laid out anew (marks, each pressed only when every selected word wears it and marking them all otherwise, from the keys too; links and sidenotes, a caret in one or words wholly inside one getting that one's own actions, and Add sidenote taking the sidenotes off words that all wear one; and after them Colour, Size and Alignment, each asked in a row of its own in the toolbar, as a link's address is: a colour is a `<TextStyle>` on the words, a block's own colour going down to its words first so that those left out keep it, a size is the paragraph's own, so Size stands only where a paragraph is selected, and an alignment (Left, Centre or Right, in Crest's icons, the button drawn in the side the words are set to) is every selected paragraph's and heading's own, the toolbar going with the words to the side they are set to; none is offered over words that are all links), `sidenotes.ts` numbers each note after its run (a widget, never text, and outside every mark the run wears, so no line drawn on the words runs under the number) and lists them for `SidenoteLayer`, `code-block.ts` puts the language picker over a block of code, and `media.ts` gives a picture or a clip a figure whose frame React fills with `MediaObject` through a portal (`media-figure.tsx`: the rail's Replace and Delete, no properties, since MDX keeps no layout), its caption written in place under it, put in and changed from `ImageInsertDialog`; the box is held at the picture's shape only when this device's media library knows its size, MDX holding none. A list's number is a button that opens `NumberToolbar`, and pressed again puts it away (`numbering.ts`): MDX keeps no continued flag, so a list counts on exactly when it starts one past the list before it, and stays there as that list grows or shrinks; Reset splits the list at the item, or joins it back. A task is a list item whose marker is a box (`tasks.ts`; the item's node view draws it in the checkbox's own classes, `CHECKBOX_BOX`, in place of the bullet or the number): `[ ]` or `[x]` and a space where a line starts makes one, in a list or out of it, Enter after a task starts one not yet done, Cmd+Enter or a press on the box ticks it or clears it, the caret staying where it was, and the slash menu's Task list makes one of the line. A block or a list item the pointer rests on shows a grip beside its first line (`moving.ts`, `components/block-grip.tsx`), an icon button's box 4px clear of the block, for which the note's pane keeps `--size-note-inset` clear on either side (the grip and 4px each side of it), so that a note that fills its pane keeps the grip whole and off the wall; it is found from where the pointer is and never from what is under it, so the grip stays while the pointer crosses the ground to it, and found again when the note is laid out anew; dragging it moves the block, never copies it, to the drop line (`bg-border-drop-line`), the drag heard by the grip's own listeners on the page from its start to its end. No line shows and nothing changes where the block already stands; an item let go beside a list is one of its items, a block let go among a list's items parts the list, the count going on past it, and the two parts are one list again once what parted them is moved away; an item dropped outside every list takes a list of the kind it left, and a list left empty goes with it; no drop is taken past the edge of what the note scrolls in, where the line would be out of sight. A move hands the note the keys, so that Cmd+Z takes it back, and a press on the grip that moves nothing gives the note back the keys it took; the selection toolbar stays through a press on the grip and steps aside only while a block is carried. An empty line has no grip, and the grip is the pointer's alone. `last-line.ts` keeps an empty paragraph after a note that ends on a list, code, a rule or a picture, so there is somewhere to type, and leaves it out of the saved text. An empty note shows the placeholder. Text pasted in is read as markdown (plain on Cmd+Shift+V), footnotes and bare addresses as above; a sidenote pasted in, read from text or copied, takes an id of its own where the note already holds its id, so the two stay two notes (`pastedSidenotes`), unless it is dragged within the note or put back inside the sidenote it was copied from. Tab steps a block that follows a list in under its last item. The body's root is one level under the `article`, so `[data-note-body] > *` in `main.css` repeats the article's 640px column (a picture breaks out to 960px, as before). `note-editor.tsx` is what the app mounts: `MdxNoteEditor`, the title over the body, MDX in and MDX back once typing rests, on Cmd+S and when the note is left, and never for a note that was only opened. A colour said by name is an ink of its own, `--ink-style-highlight`, `-muted`, `-danger`, `-warning` and `-success`, each on the ink of its role.

## Sign-in and the Worker

- Sign-in is the OAuth native-app flow, because Google refuses passkeys inside embedded windows: main opens the default browser at Google's consent screen with PKCE, listens on a loopback port for the one redirect (`services/google-sign-in.ts`), hands the code to the Worker's `POST /auth/google/code`, and stores the session it answers with (`services/session.ts`). The Worker holds the OAuth client secret; the app holds no Google configuration and asks `GET /auth/google/config` for the client id. The renderer only ever sees the user (`window.api.auth`), never a token.
- `services/api.ts` is the one door to the Worker: the deployed URL by default, `MAIN_VITE_API_URL` in `.env` to override it (`http://127.0.0.1:8787` against `npm run dev` in `worker/`), bearer attached, non-2xx raised as `ApiError` with the Worker's error code.
- Routes, limits, error codes and the D1 schema: `worker/README.md`. Change the contract there first, then both sides.

## Media pipeline

- Renderer code never talks to the Worker. It calls `@/lib/media` (`uploadMediaFile`, `listMediaAssets`, `updateMediaAlt`, `updateMediaFilename`, `deleteMedia`, `uploadPoster`), which crosses to main over `window.api.media` (typed in `src/renderer/src/env.d.ts`).
- Main saves every file to `userData/media/<uuid>-<safe-name>` first and records it in the `media_assets` SQLite table. `local://<file>` is served by the `local` protocol in `src/main/index.ts`.
- When the API is configured and a session exists (`isMediaApiAvailable` in `services/media-api.ts`) and the machine is online, the same call PUTs the bytes and metadata to the Worker in one request under key `media/<uuid>-<safe-name>` and returns the public URL the Worker answers with. Otherwise the asset is returned with its `local://` URL and queued; `media.flushPending` uploads later and rewrites `local://` sources inside note bodies to the public URL, a replace of the address in the body's text: a note in MDX spells an address as markdown escapes it (a file name's brackets), so that spelling (`mdxDestination` in `@shared/mdx/dialect`) is replaced too.
- The Worker files objects per user (`u/<userId>/<key>`) and serves bytes itself at `/m/...`; the app never sees the bucket key and treats a URL as opaque.

## Storage and sync

- SQLite `notes`: `body` is the note's MDX text and `plain_text` its words, derived on every write for FTS (`notes_fts` indexes title, tags, plain_text). `db/migrations.ts` makes a new database whole at the current version (`createSchema`) and keeps only the steps that bring an earlier build's database up to it: v7 drops the notes already deleted (but one whose deletion the Worker has yet to hear) and the `format` and `body_backup` columns. `services/notes.ts` keeps a body as it came and reads it only for its words (`mdxPlainText`, so the MDX packages, ESM-only, are bundled into main: `externalizeDeps.exclude` in `electron.vite.config.ts`); a note made with no body (`createNote`, as the app makes one) starts empty.
- The Worker's D1 `notes` table holds `{ title, body, tags, createdAt, updatedAt, isDeleted }` per user; `body` is the same MDX string, which the Worker stores as sent and never reads, checking only its size. Deletions are tombstones (`isDeleted`), never row deletes, so they reach every device.
- Sync lives in main (`services/sync.ts`) and is a poll every minute plus a push on every save: push each dirty note with `PUT /notes/<id>` (the Worker stamps `updatedAt`), flush pending media, then pull `GET /notes` from the stored cursor (`app_meta.sync_cursor`) and apply a remote note when its `updatedAt` is newer than the local one. A pull that changed anything sends `sync:changed` to the window, which reloads the list. Sync only runs with a session; offline, edits queue in `sync_queue`.

## Note assistant (Gemma)

- The right-hand rail (`components/assistant-sidebar.tsx`), toggled from the top bar, resized from its edge with the note as the sidebar is (`useSidebarResize` with `ASSISTANT_RAIL`: 320 to 480px, widening leftward, remembered under `assistantWidth`) and standing on the glass where the window is frosted (AppKit's inspector on macOS 27, see Frosted shell), chats about the open note with Gemma 4 E4B, run by main through node-llama-cpp (`services/llama-engine.ts`, imported on first use; Metal on macOS). The rail always opens on its composer, the send button at the box's right, the conversation stacked up from the box; under the box stand the model, the effort (low answers at once, medium and high think first, capped by `EFFORT_THOUGHT_TOKENS`; remembered under `assistantEffort`) and a ring metering the context window the next request starts with, with no count beside it (`assistant.usage`: counted by the model's tokenizer once it is loaded, estimated from the text before that). The model is never packaged: while no copy is on disk, a line over the box says the first message downloads it, and main does (`ensureModel` in `services/assistant.ts`), keeping the turn only once the model is there; Stop during the download cancels it and hands the prompt back to the box. Settings lists every copy on the machine with its size and source, and deletes one on a confirm (`assistant.models`, `assistant.deleteModel`: only a path the locator found; a Hugging Face snapshot goes with its blob, and Ollama's copy is left to Ollama).
- Before offering it, main looks for a copy another app already has (`services/model-locator.ts`): the Hugging Face hub cache, LM Studio, Ollama's `gemma4:e4b*` manifests, llama.cpp's download cache and node-llama-cpp's models folder, honouring `HF_HUB_CACHE`/`HF_HOME`, `OLLAMA_MODELS` and `LLAMA_CACHE`. A candidate counts only if its GGUF header says `gemma4` (`services/gguf.ts`).
- The download (`services/model-download.ts`) is Google's QAT q4_0 file pinned by commit and sha256 (`GEMMA_MODEL` in `@shared/domain/assistant`), written into the Hugging Face cache in its own layout (`blobs/<sha256>` plus a `snapshots/<commit>/<file>` link; the file itself on Windows) so other tools find it. It resumes from `blobs/<sha256>.incomplete` and checks free space first.
- Each prompt carries the note as saved in SQLite (title + plain text, capped) and the last 20 turns. Conversations live in the `assistant_messages` table (migration v4), per note, on this device only: never queued, never sent to the Worker, and deleted with their note. "Insert into note" reads the Markdown reply as pasted markdown is read and appends it to the open note's ProseMirror view, over any empty lines the note ends on (`prose/insert-reply.ts`).
- Packaging: `electron-builder.yml` keeps only the target's node-llama-cpp binaries and unpacks them from the asar.
